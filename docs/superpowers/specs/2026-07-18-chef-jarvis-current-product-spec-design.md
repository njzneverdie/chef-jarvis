## 1. 文件定位

本文件根據目前正式站、工作區程式、README、Supabase migrations、Edge Functions 與自動測試反向整理。它描述目前已實作或已有程式合約的產品行為，不代表未來 Roadmap。

驗收證據分為：

- **正式站實測**：已在登入狀態下檢查正式站畫面與唯讀流程。
- **自動測試**：目前 `npm test` 共 71 項，71 項通過。
- **瀏覽器測試**：Playwright 公開流程通過；登入七頁唯讀流程需專用測試帳號。
- **程式驗證**：從前端、Edge Function、migration 或安全設定確認。
- **待正式 E2E**：涉及寄信、AI/USDA 配額消耗或雲端資料異動，本次未實際觸發。

## 2. 產品定義

Chef Jarvis 是一個需要登入的雙語 Web/PWA 個人料理助手。產品將使用者的營養目標、健康目標、飲食需求、過敏原、不喜歡的食材、廚房設備與現有庫存，串成完整料理流程：

```text
建立個人資料
→ 輸入料理需求
→ 產生個人化食譜
→ 檢查並套用替換食材
→ 建立購物清單
→ 將採買品加入庫存
→ 排入一週餐期
→ Chef Mode 引導烹飪
→ 記錄營養、扣除庫存與留下評分
```

目標使用者是希望依個人營養、飲食限制與現有設備規劃餐點，並需要實際採買、烹飪和營養追蹤流程的家庭料理者。

## 3. 現行系統邊界

- 前端：Cloudflare Pages 上的 Vanilla JavaScript PWA。
- 身分與資料：Supabase Auth、Postgres、Row Level Security。
- AI：Supabase Edge Function 呼叫 Gemini。
- 營養佐證：Supabase Edge Function 呼叫 USDA FoodData Central。
- 圖片：Wikimedia Commons，須保留來源、作者、授權及圖片符合度標示。
- 正式前端來源：`chef-jarvis-netlify-web/public/`。
- `chef-jarvis-codex/` 為歷史原型，不納入本規格。
- 原生 iOS/Android App、管理後台、照片辨識庫存與產品分析不在目前範圍。

## 4. 功能規格與驗收標準

### 4.1 帳號與登入

產品支援 Email/Password 註冊、確認信、登入、登出、忘記密碼與更新密碼。

- [ ] 未登入使用者只能看到登入／註冊介面。
- [ ] Email 格式不合法時不得送出。
- [ ] 註冊密碼少於 8 字元時不得送出。
- [ ] 登入、註冊與密碼更新失敗時顯示可理解的錯誤。
- [ ] 註冊成功但尚未建立 session 時，提示使用者開啟確認信。
- [ ] 忘記密碼必須先輸入合法 Email。
- [ ] 重設密碼連結返回後可設定至少 8 字元的新密碼。
- [ ] 登出後清除前端使用者狀態並返回登入畫面。
- [ ] 料理進行中登出前須顯示確認，並說明進度仍會保留。
- [ ] 所有私人頁面與 Edge Function 都要求有效登入狀態。
- [ ] 使用者可在 Profile 永久刪除帳號，且必須精確輸入 `DELETE`。
- [ ] 刪除帳號由驗證 JWT 的 Edge Function 執行，service-role 金鑰不得進入瀏覽器。
- [ ] Auth 使用者刪除後，所有連結的產品資料須由 foreign key cascade 一併刪除。
- [ ] 正式站完整註冊寄信與密碼重設流程標記為「待正式 E2E」。

### 4.2 初次設定與個人資料

首次登入且尚未完成 onboarding 的使用者必須建立料理與營養資料。

支援資料：

- 身高 100–250 cm。
- 體重 30–350 kg。
- 年齡 13–120 歲。
- 生理性別。
- 低、中、高活動量。
- 維持、減脂、增肌、增肌減脂目標。
- 系統計算或自訂營養目標。
- Vegetarian、Vegan、Halal。
- 乳糖不耐、無麩質、堅果與甲殼類過敏。
- 不喜歡的食材。
- 可用廚房設備。

驗收：

- [ ] 缺少身高、體重或年齡時不得完成 onboarding。
- [ ] 空白、`NaN`、Infinity 或超出範圍的營養數值不得儲存。
- [ ] 系統計算模式使用 Mifflin–St Jeor 基礎代謝公式。
- [ ] 活動量與目標調整正確套用。
- [ ] 增肌目標採較高蛋白質配置。
- [ ] 脂肪約占總熱量 27%，碳水補足剩餘熱量。
- [ ] 計算結果不得產生負碳水。
- [ ] 自訂模式允許使用者輸入熱量、蛋白質、碳水與脂肪。
- [ ] 過敏原、飲食需求、不喜歡食材與設備均持久化。
- [ ] onboarding 不得以 Esc 意外跳過。
- [ ] 個人資料載入失敗時，不得誤開 onboarding 或覆蓋既有資料。

### 4.3 首頁與每日摘要

登入後首頁提供料理輸入、快捷提示、每日營養目標與今日攝取進度。

- [ ] 顯示目前熱量與蛋白質目標。
- [ ] 顯示今日熱量、蛋白質、碳水與脂肪攝取。
- [ ] 今日日期使用使用者本地日期，而非 UTC 日期。
- [ ] 快捷提示依目前語言填入相對應文字。
- [ ] 料理要求不得為空，最長 500 字。
- [ ] 產生期間按鈕停用並顯示階段性進度。
- [ ] 8 秒與 22 秒後更新等待提示。
- [ ] 使用者可從首頁開啟快速營養記錄。
- [ ] 營養資料載入失敗不應使整個首頁失效。

### 4.4 AI 個人化食譜

系統從伺服器重新讀取使用者 profile、pantry、近期食譜及回饋，再交給 Gemini 規劃。

食譜至少包含：

- 標題、摘要、時間與份數。
- 整份料理的熱量與巨量營養素估算。
- 精確食材名稱。
- 數量、單位、處理方式與分類。
- USDA 英文查詢名稱。
- 完整料理步驟。
- 真正烹煮／等待步驟的計時器。
- 個人化食材替換。
- 設備替代方式。
- 剩餘食材再利用建議。
- 合法圖片與授權資訊。

驗收：

- [ ] 瀏覽器不得自行提交可偽造的 profile 或 pantry 作為權威資料。
- [ ] 過敏原優先於口味回饋、庫存與使用者自由文字。
- [ ] AI 不得建議已記錄的過敏原或明確飲食禁忌。
- [ ] 不得使用模糊的「雞肉」「蔬菜」「調味料適量」作為新食譜主要食材。
- [ ] 食材須分開保存名稱、數量、單位與處理方式。
- [ ] 支援的單位限於可執行的重量、容量與件數單位。
- [ ] 上限為 60 項食材、40 個步驟、8 組替換及 4 組再利用建議。
- [ ] 料理計時器必須對應同一步驟中明確寫出的時間。
- [ ] 閱讀食譜、備料、切菜、擺盤或清潔不得產生食譜計時器。
- [ ] 同一步驟有多段時間時，須保留多個依序排列的計時器。
- [ ] 泛用餐點請求須避開近期重複菜色。
- [ ] 明確指定菜名時可重複既有菜色。
- [ ] AI 回傳資料必須通過 shape、數值、長度、單位、timer 與 substitution 驗證。
- [ ] 單一無效 timer 或 substitution 應被移除，不得使整份合法食譜失效。
- [ ] 圖片只能使用 HTTPS 與核准的 Wikimedia 主機。
- [ ] 圖片必須顯示來源、作者與授權資訊。
- [ ] 圖片必須帶有 `exact`、`representative` 或 `curated` 符合度。
- [ ] 廣泛料理家族 fallback 必須標示「Representative dish image」，不得冒充精確成品照片。
- [ ] 食譜產生前端總等待時間上限為 50 秒。
- [ ] Gemini 第一模型 12 秒失敗後切換第二模型，第二模型上限 20 秒。
- [ ] Gemini 未設定、逾時或兩個模型失敗時回傳有明確標示的完整 fallback 食譜。
- [ ] fallback 食譜仍須有精確份量、購物項目、料理步驟與安全限制。
- [ ] AI 食譜正式站產生與配額消耗標記為「待正式 E2E」。

### 4.5 AI 配額與降級

- [ ] 每位使用者每分鐘最多 5 次 AI 食譜請求。
- [ ] 每位使用者滾動 24 小時最多 100 次。
- [ ] 超過配額回傳 HTTP 429 與 `Retry-After`。
- [ ] 配額資料不可由匿名或一般 authenticated role 直接讀寫。
- [ ] 所有 Gemini 模型失敗後，已消耗的配額應退還。
- [ ] 配額服務本身不可用時，顯示服務暫時不可用，不得假裝成功。
- [ ] fallback 必須明確標示，不能掩蓋 AI 失敗狀態。

### 4.6 食譜替換與儲存

- [ ] 替換建議須說明原食材、替代食材及理由。
- [ ] 使用者必須主動套用替換。
- [ ] 套用時同步更新食材、數量、單位、USDA query、購物項目、步驟與計時器。
- [ ] 所有仍提到原食材的步驟都必須提供安全更新。
- [ ] 不完整替換不得顯示為可安全套用。
- [ ] 過敏相關替換後仍提示使用者檢查包裝標示。
- [ ] 產生的食譜自動嘗試儲存到使用者帳號。
- [ ] 儲存失敗時食譜仍可立即使用，但須提示尚未保存。
- [ ] 切換頁面或重新整理後可載入最近食譜或本機快取。
- [ ] 使用者可查看已儲存食譜並重新開始烹飪。

### 4.7 USDA 營養佐證

USDA 查詢在食譜先顯示後於背景執行，不阻塞料理流程。

- [ ] 每項食材優先使用 AI 產生的英文 `usda_query`。
- [ ] 每次最多查詢 30 項食材。
- [ ] 每項 USDA 查詢逾時上限為 5 秒。
- [ ] 搜尋多筆候選並依名稱覆蓋率、資料類型與營養合理性排序。
- [ ] 優先 Foundation、SR Legacy 與 FNDDS。
- [ ] 對 fried、breaded、with sauce 等不相符加工品降權。
- [ ] 名稱覆蓋率不足 50% 時視為沒有可靠匹配。
- [ ] 顯示每 100 g 參考值、實際匹配名稱、資料類型與匹配分數。
- [ ] 依食材實際份量換算整份料理營養。
- [ ] 顯示資料覆蓋率。
- [ ] USDA 與食譜估算熱量差異超過 35% 時提出警告。
- [ ] 蛋白質差異超過 40% 時提出警告。
- [ ] USDA 無結果或不可用時，食譜與購物清單仍可使用。
- [ ] 食材未變更時重用已保存 USDA 結果。
- [ ] USDA 每位使用者每分鐘最多 60 lookup units、24 小時最多 300 units。
- [ ] USDA 配額超限回傳 HTTP 429 與 `Retry-After`。

### 4.8 購物清單

- [ ] 從食譜建立獨立購物清單。
- [ ] 每項顯示名稱、數量與單位。
- [ ] 同名且可換算單位的品項可合併。
- [ ] 不相容單位不得靜默合併。
- [ ] 小量液體可顯示為茶匙／湯匙等採買友善單位。
- [ ] 使用者可逐項勾選。
- [ ] 顯示完成項目數與總數。
- [ ] 可刪除整份清單，刪除前須確認。
- [ ] 只有已勾選品項可加入 pantry。
- [ ] 加入庫存後提供進入料理流程的下一步。
- [ ] 與食譜連結的清單可返回對應食譜開始烹飪。

### 4.9 Pantry 庫存

- [ ] 使用者可手動新增食材。
- [ ] 食材名稱不得為空且最長 120 字。
- [ ] 手動新增預設保存於 fridge。
- [ ] 購物清單品項可批次加入庫存。
- [ ] 相同名稱及可相容單位應合併數量。
- [ ] 單位不相容時須提示，不得靜默建立錯誤數量。
- [ ] AI 產生食譜前會讀取現有庫存。
- [ ] 完成料理後依可換算的食譜用量扣除庫存。
- [ ] 扣除至零時可移除庫存項目。
- [ ] 自動扣除必須可見且可復原。
- [ ] 網路錯誤不得讓使用者誤以為庫存已更新。

### 4.10 一週餐期

目前 UI 為一週七天、每天一個晚餐欄位。

- [ ] 顯示當週星期一至星期日。
- [ ] 使用者可從已儲存食譜選擇餐點。
- [ ] 可設定實際料理份數。
- [ ] 同一日期的 dinner 不得重複建立多筆。
- [ ] 合併購物清單依排定份數比例縮放食材。
- [ ] 沒有任何已排餐點時，合併購物清單按鈕停用。
- [ ] 顯示首次使用的三步驟說明。
- [ ] 顯示已收藏的剩餘食材料理靈感。

### 4.11 Chef Mode

- [ ] 未選擇食譜時顯示空狀態與規劃 CTA。
- [ ] 一次顯示一個主要步驟與完整步驟佇列。
- [ ] 支援上一步、下一步、跳到指定步驟及重複朗讀。
- [ ] 開始另一道料理前確認，不得直接覆蓋現有進度。
- [ ] 食譜計時器與原始步驟及順序保持關聯。
- [ ] 同一步驟可有多個依序顯示的食譜倒數。
- [ ] 使用者可手動新增倒數或 stopwatch。
- [ ] 每個計時器可獨立開始、暫停、重設及移除。
- [ ] 多個計時器可同時執行且互不覆寫。
- [ ] 倒數不得小於零；stopwatch 必須遞增。
- [ ] 無執行中計時器時停止全域 ticker。
- [ ] 計時器完成時提供畫面提示、聲音及標題閃爍。
- [ ] 使用者授權通知後，完成時顯示系統通知。
- [ ] 通知、音訊、語音或 Wake Lock 不支援時仍可完成核心料理流程。
- [ ] 語音朗讀語系依目前中英文內容設定。
- [ ] 語音控制支援下一步、重複與開始計時。
- [ ] Jarvis 朗讀時暫停語音辨識，避免自己觸發自己。
- [ ] 無法辨識的廚房聲音不得持續顯示錯誤 toast。
- [ ] 進入料理畫面時嘗試取得 Screen Wake Lock。
- [ ] 離開料理畫面時釋放 Wake Lock。
- [ ] 進度與 timers 保存到 localStorage。
- [ ] 登入時同步 active cooking session 到 Supabase。
- [ ] 重新整理或跨裝置後恢復最新有效進度。
- [ ] 完成或放棄時更新 cooking session 狀態。

### 4.12 料理完成、營養與回饋

- [ ] 完成最後步驟後立即結束料理狀態。
- [ ] 使用使用者本地日期建立 nutrition log。
- [ ] 預設記錄一份，可調整為 0.25–12 份。
- [ ] 有 USDA 整餐結果時使用 USDA，否則使用食譜估算。
- [ ] 完成後自動嘗試扣除 pantry。
- [ ] 營養記錄或 pantry 更新失敗時仍立即顯示回饋視窗。
- [ ] 回饋支援 1–5 星。
- [ ] 備註最長 300 字。
- [ ] 使用者可略過評分但仍調整實際食用份數。
- [ ] 回饋只能作為軟性口味資料，不得覆蓋過敏與飲食限制。
- [ ] 首頁今日營養進度在記錄後更新。
- [ ] 快速記錄支援已儲存食譜與手動估算。
- [ ] 手動記錄熱量必須大於零，其他營養值不得為負數。

### 4.13 個人資料、設備與資料匯出

- [ ] 顯示健康目標、營養目標、飲食需求與過敏標籤。
- [ ] 可重新編輯完整 onboarding 資料。
- [ ] 可獨立更新廚房設備。
- [ ] 設備更新會影響後續食譜設備替代建議。
- [ ] 使用者可下載 JSON 格式資料。
- [ ] 匯出包含 profile、pantry、recipes、shopping lists、weekly plans、cooking sessions、nutrition logs、feedback 與 saved meal cards。
- [ ] 匯出查詢只能取得目前使用者的資料。
- [ ] 任一資料集合查詢失敗時不得產生不完整且未說明的匯出檔。
- [ ] Profile 顯示資料保留政策與帳號永久刪除入口。
- [ ] 刪除成功後清除該帳號的本機烹飪、食譜快取與語音提示資料。

## 5. 跨領域發布門檻

### 5.1 雙語與無障礙

- [ ] UI 可切換英文與繁體中文。
- [ ] 語言選擇保存到 localStorage。
- [ ] `<html lang>` 隨語言更新。
- [ ] AI 食譜語言跟隨目前介面語言。
- [ ] 主要動態表單 label 與 input 有程式化關聯。
- [ ] Modal 具有 dialog 語意及可辨識標題。
- [ ] 一般 modal 可用背景或 Esc 關閉。
- [ ] onboarding 不可用 Esc 跳過。
- [ ] disabled 按鈕具有明顯狀態。
- [ ] 動態進度訊息使用 live region 或等效可讀方式。

### 5.2 資料安全與隱私

- [ ] 前端只包含 Supabase publishable key。
- [ ] Gemini、USDA 與 service-role 金鑰不得出現在公開資產。
- [ ] Edge Functions 驗證 Bearer JWT。
- [ ] Edge Functions 僅接受允許來源與 POST/OPTIONS。
- [ ] 所有使用者資料表啟用 RLS。
- [ ] 直接擁有的資料以 `auth.uid() = user_id` 或等效條件隔離。
- [ ] Shopping/meal-plan 子項目透過父資料所有權隔離。
- [ ] UPDATE policy 同時限制既有資料與新資料所有權。
- [ ] AI/USDA quota 函式僅授權 service role。

## 6. 已知缺口與差異

原缺口已依可控範圍修正或收斂：

- **舊資料已受控**：舊食譜／購物清單仍可能缺少精確食材份量，但現在會顯示警告；不得直接開始 Chef Mode、建立新清單或加入 pantry，直到重新產生精確食譜。系統不猜測舊資料份量。
- **瀏覽器 E2E 已建立**：公開登入殼、驗證、語言保存與隱私頁由 Playwright 自動檢查；登入後七頁唯讀 smoke test 在提供專用帳號時執行。
- **Edge 部署可驗證**：三支 Edge Function 提供版本標頭，`npm run verify:deployment` 會連同四個前端核心檔案 SHA-256 一併比對。新版尚未部署前，此檢查應失敗且不可宣稱正式環境已同步。
- **離線範圍已揭露**：離線時有明確狀態列。本機料理進度可用，但登入、雲端同步、AI 與 USDA 仍需要網路；產品並未承諾完整離線。
- **帳號刪除已實作**：前端二次確認、JWT 驗證 Edge Function、Auth admin 刪除、資料 foreign-key cascade、localStorage 清除與 `PRIVACY.md` 資料保留政策均已加入。正式驗收仍需先套 migration 並部署 deletion function。
- **圖片不確定性已揭露**：Wikimedia exact、representative 與 curated 結果分級；廣泛 fallback 會標示為相似料理示意照片。仍不保證每道菜都有可驗證的精確圖片，無合格圖片時採無圖版面。
- **歷史路徑保留**：工作區目錄仍含 `netlify-web`，避免破壞既有本機與部署路徑；tracked Supabase project ID 與 Cloudflare project name 已統一為 `chef-jarvis`。

仍需要外部憑證或部署後證據的項目：

- 本次沒有消耗正式 AI/USDA 配額或修改正式雲端資料；完整生成、採買、烹飪、刪除 E2E 必須使用可丟棄的專用帳號。
- Cloudflare Pages、migration 與三支 Edge Function 必須部署後，才可讓 `npm run verify:deployment` 通過。
