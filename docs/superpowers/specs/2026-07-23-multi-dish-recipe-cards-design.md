# Chef Jarvis 多道菜獨立食譜卡設計

日期：2026-07-23  
狀態：已核准

## 背景與根因

目前 `chef-meal-plan` 只有兩種請求分類：

- `named_dish`：一個明確菜名。
- `broad_request`：請系統推薦一道料理。

輸入 `宮保雞丁、排骨蛋炒飯、炒高麗菜` 時，解析器把整串文字分類成一個 `named_dish`。後續菜名驗證因此要求產生結果的標題必須等於整串輸入，Gemini 產生的多道菜標題則在 `repair_validation / dish_title` 被拒絕。現有提示詞雖然要求模型涵蓋多道菜，但資料模型、解析器、驗證器和前端狀態仍只支援單一食譜。

這不是缺少某幾道菜的別名，而是缺少正式的「多道菜菜單」資料型態。繼續加入菜名特例無法解決問題。

## 已評估方案

### 方案一：後端批次處理並回傳獨立食譜結果

Edge Function 辨識整份菜單，拆分菜名，讓每一道菜分別走既有的具名食譜產生與驗證流程，最後回傳多個獨立結果。

優點：

- 後端、前端和安全閘門對多道菜有一致契約。
- 每道菜仍接受完整的菜名、食材、限制和過敏原驗證。
- 可以支援部分成功與單項重試。
- 單一道菜流程可維持向後相容。

代價：

- 需要抽出可重複呼叫的單一道菜產生流程。
- 同一請求可能同時呼叫多次模型，必須限制數量與並行度。

### 方案二：前端拆分後逐一呼叫現有 API

前端自行拆菜名，再為每道菜呼叫一次目前的單一道菜 API。

優點是修改範圍較小；缺點是菜單解析只存在前端，直接呼叫 API 仍會重現錯誤，額度、取消、部分失敗和診斷也會分散。此方案不符合「整個系統正確處理」的目標。

### 方案三：背景工作與佇列

每道菜建立背景工作，前端逐步接收完成結果。此方案最能支援大型菜單，但會新增工作資料表、狀態同步、逾時清理與輪詢／即時更新，超過目前最多六道菜的需求。

## 採用方案

採用方案一：後端批次處理，前端顯示每道菜一張獨立食譜卡。

## 產品行為

### 請求辨識

新增第三種請求型態 `menu`。

系統只以明確分隔符辨識多道菜：

- 中文頓號 `、`
- 中文或英文逗號 `，`、`,`
- 中文或英文分號 `；`、`;`
- 換行
- 全形或半形加號 `＋`、`+`

系統不以自然語言中的「和」、「與」或 `and` 自動分割，避免把 `mac and cheese` 等單一菜名拆錯。

解析後規則：

- 正規化 Unicode、空白與項目前後標點。
- 移除空項目。
- 以正規化後的完整名稱去除重複項目。
- 一個項目沿用目前的單一道菜流程。
- 二至六個項目分類為 `menu`。
- 超過六道菜回傳 `400 menu_too_large`，不靜默截斷。
- 任一非空項目超過 160 個字元時回傳 `400 invalid_menu_item`；重複分隔符產生的空項目直接忽略。
- 不靠硬編碼菜名判斷是否為菜單。

### 產生流程

`menu` 請求先讀取一次使用者資料、庫存、偏好和最近菜色，再將相同的安全上下文提供給每一道菜。

每個菜單項目分別執行：

1. 建立單一道菜解析結果。
2. 必要時進行菜名解析與澄清判斷。
3. 查詢可用的外部食譜來源。
4. 產生完整食譜。
5. 必要時修復格式或可修復欄位。
6. 驗證菜名、核心食材／技法、資料完整性、飲食限制和過敏原。
7. 通過出口過敏原閘門後才加入成功結果。

後端最多同時處理三道菜。超過三道時分批處理，所有工作共用請求截止時間。截止時間到達時，未完成項目標記為可重試失敗，已完成項目照常回傳。

### 額度與取消

- 一次菜單送出視為一次餐點規劃操作，沿用目前一次請求的一次額度。
- 若整份菜單在任何食譜產生前失敗，沿用目前的安全退款流程。
- 已產生至少一張合格食譜卡時不退款。
- 使用者取消請求或帳號狀態改變時，所有仍在進行的菜單項目一起失效，舊結果不得寫入新工作階段。

### 回傳契約

單一道菜成功時維持目前的 `{ plan, ... }` 回傳格式，避免破壞既有前端和測試。

多道菜回傳：

```json
{
  "request_type": "menu",
  "original_request": "宮保雞丁、排骨蛋炒飯、炒高麗菜",
  "recipes": [
    {
      "requested_dish": "宮保雞丁",
      "status": "ready",
      "plan": {}
    },
    {
      "requested_dish": "排骨蛋炒飯",
      "status": "ready",
      "plan": {}
    },
    {
      "requested_dish": "炒高麗菜",
      "status": "unavailable",
      "code": "named_recipe_unavailable",
      "message": "目前無法取得完整食譜，請稍後再試。",
      "meta": {
        "failure_stage": "repair_validation",
        "failure_reason": "recipe_schema"
      }
    }
  ],
  "meta": {
    "requested_count": 3,
    "ready_count": 2,
    "clarification_count": 0,
    "failed_count": 1
  }
}
```

每個 `recipes[]` 項目的 `status` 只能是：

- `ready`：必須包含完整且已通過安全驗證的 `plan`。
- `clarification_required`：只包含原始項目、候選菜名或補充描述提示，不得包含 `plan`。
- `unavailable`：只包含安全錯誤訊息和固定診斷碼，不得包含 `plan`。

HTTP 狀態：

- 所有項目成功：`200`
- 至少一項成功、其他項目失敗：`200`
- 至少一項需要澄清、其他項目成功或需要澄清：`200`
- 所有項目均為安全且可理解的澄清需求：`200`
- 所有項目均為 `unavailable`：`503`
- 菜單格式或數量不合法：`400`
- 認證、設定或個人安全資料讀取失敗：維持目前的全請求失敗狀態，不啟動任何菜色產生。

錯誤回傳不得包含模型原文、個人資料、過敏原設定或供應商內容。

## 安全設計

### 菜名與完整性

- 每道菜以自己的 `requested_dish` 建立 `named_dish` 解析結果。
- 每道菜的標題驗證只與自己的菜名比較，不與整份菜單字串比較。
- 每道菜仍需通過既有核心食材與核心技法驗證。
- 未通過的菜不得以相近菜色、通用飯碗或備用餐點冒充成功。

### 過敏原與飲食限制

- 每張食譜卡在進入 `recipes[]` 前執行現有過敏原出口閘門。
- 最終回應序列化前，再對所有 `status: "ready"` 的 `recipes[].plan` 執行防禦性總檢查。
- 某一道菜被安全閘門拒絕時，只能成為不含食譜內容的失敗項目，不能回傳部分食材或步驟。
- 若程式錯誤讓未檢查的成功項目進入回應，最終閘門須令整個回應失敗關閉。
- 單一道菜與所有 fallback／澄清／部分成功路徑仍必須經過同一個 `safeRespond` 出口。

## 前端設計

新增 `menuPlans` 狀態，單一道菜仍使用現有 `currentPlan`。

多道菜結果區依輸入順序顯示食譜卡：

- 菜名
- 圖片或圖片載入狀態
- 時間、份量和營養摘要
- 「查看食譜」
- 「開始烹飪」
- 「加入購物清單」
- 失敗項目的「單獨重試」

點擊一張成功卡後，將該卡的 `plan` 設為目前食譜，沿用既有食譜詳情與 Chef Mode，不建立另一套烹飪流程。

其他規則：

- 卡片逐項顯示成功或失敗，不以一個通用錯誤遮蔽整份菜單。
- 單獨重試只送出該菜名，成功後只替換對應卡片。
- 儲存、購物清單、營養紀錄和開始烹飪都以單張卡為單位。
- 同時已有進行中的烹飪時，沿用現有確認保護。
- 切換帳號、登出或產生上下文失效時清除所有 `menuPlans`。
- 語言切換後，卡片控制文字更新；已產生的食譜內容不在前端自行翻譯。

## 觀測與診斷

菜單層級紀錄：

- 請求 ID
- 請求型態
- 菜色數量
- 成功、澄清與失敗數量
- 總耗時

菜色層級紀錄：

- 以不可逆雜湊表示的菜色觀測鍵
- 菜單索引
- 結果
- 失敗階段與固定原因碼
- 耗時

不得記錄原始菜名、使用者個人資料、過敏原清單、模型原文或完整食譜。

## 驗收標準

### 解析與相容性

- `肉燥飯` 仍被分類為單一道菜。
- `宮保雞丁、排骨蛋炒飯、炒高麗菜` 被解析為三個項目且順序不變。
- 中文逗號、英文逗號、分號、換行與加號均可分隔。
- 多餘空白和重複分隔符不產生空白菜色。
- 重複菜色只產生一張卡。
- `mac and cheese`、`fish and chips` 不被拆分。
- 七道菜得到明確的 `menu_too_large`，不產生任何食譜。

### 產生與驗證

- 每個項目獨立取得 canonical name、來源、完整食材和步驟。
- 每個成功標題只需符合自己的 requested dish。
- 三道菜不能被合併成一個通用食譜。
- 不得因某一道失敗而隱藏其他成功食譜。
- 所有失敗時顯示逐項可重試狀態。
- 單一道菜的既有成功、修復、澄清和失敗契約保持不變。

### 安全

- 對所有單一道菜與多道菜回傳路徑，使用者過敏原家族不得出現在任何成功卡片的 ingredients、替代食材或步驟中。
- 部分失敗回應中的失敗項目不得含有 plan、ingredients 或 steps。
- 最終出口閘門必須拒絕任何繞過逐項檢查的危險成功卡片。
- 飲食限制、過敏原資料無法安全讀取時，整份請求在模型呼叫前失敗。

### 前端

- 三道菜顯示三張獨立卡片。
- 每張卡可獨立查看、重試、加入購物清單、儲存及開始烹飪。
- 單獨重試不重新產生已成功的其他卡片。
- 登出、切換帳號或新請求開始時不會顯示上一位使用者或上一個請求的卡片。

### 正式站驗證

部署後至少執行以下正式站案例：

1. `宮保雞丁、排骨蛋炒飯、炒高麗菜`
2. 一組先前未硬編碼的中文菜單，例如 `紅燒牛肉麵、麻婆豆腐、蒜炒空心菜`
3. 一組英文菜單，例如 `beef bourguignon, Caesar salad, garlic bread`
4. 單一道菜 `肉燥飯`
5. 含 `and` 的單一道英文菜名 `mac and cheese`

每個案例須檢查回傳數量、卡片標題、完整食材、完整步驟、單項操作和安全診斷。不得以單次成功作為完成證據；前三個多道菜案例至少各重複兩次。

## 非目標

- 不新增永久菜單資料表。
- 不支援超過六道菜的大型宴席排程。
- 不同時開始多個 Chef Mode 烹飪工作階段。
- 不以硬編碼方式加入所有可能菜名。
- 不降低菜名、核心食材、飲食限制或過敏原驗證來提高表面成功率。
